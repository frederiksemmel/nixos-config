# 3. One async core, two frontends

Date: 2026-11-15. Status: accepted.

## Context

The TV app's state lived inside its Slint UI. `App` in `src/app.rs` ran on the
UI thread and owned the library, profiles and progress, the mpv player,
HDMI-CEC and the TV, storage and downloads. The web app's requests were queued
onto the UI thread and answered there. So:
- a phone's request waited behind the TV's screen;
- database writes and mpv IPC ran on the UI thread;
- Toasty, which is async only, needed a sync bridge: a runtime of its own and
  a channel per call ([ADR 2](0002-toasty.md)).

## Decision

The app is one async core on Tokio and two frontends that use the same
interface (`src/core/`).

- **The core** owns all state and hardware: the library, every profile's
  progress, the database, the player, CEC and the TV, audio and headphones,
  voice, the offline cache and downloads. One task, the actor, holds the
  state and takes one input at a time, so nothing needs a lock.
- **The interface** is the `Core` handle:
  - `core.send(Request)` and `core.ask(Request).await -> Outcome`: typed
    commands. `send` never blocks.
  - `core.subscribe()`: the stream of `bus::Event`s (playback, voice, audio,
    which screen plays, and for the TV's own screen `Home`, `Key`, `Message`
    and `Panel`).
  - snapshots of what the core last published: `library()`, `progress(who)`,
    `home()`, `now_playing()`, `screen()`, `storage()`.
- **The web frontend** (`src/api.rs` and the routes beside it) turns HTTP and
  the WebSocket into those calls. It runs on the core's runtime.
- **The Slint frontend** (`src/ui.rs`) holds only what is on screen: the
  focus, the open page, the profile picker, loaded artwork. It draws from
  the `Home` snapshot the core sends, sends keys and choices with
  `core.send`, and receives events through `upgrade_in_event_loop`. The UI
  thread never waits for the core.

Slint's own `spawn_local` can't run Tokio futures without `async_compat`, so
Tokio stays on the core's threads and the two sides meet over channels.

## Consequences

- **The database is async.** `Db`'s methods await Toasty directly; the bridge
  and the in-memory auth store are gone, and auth tests run on an in-memory
  SQLite database.
- **Drivers keep their threads.** mpv's reader, CEC's poll loop, the voice
  capture, bluetoothctl and the read-ahead fetcher are blocking code. Each
  reports into the core's queue as a `Signal`, and the core calls their
  short blocking methods with `block_in_place` or `spawn_blocking`. Rewriting
  them on Tokio would change nothing a viewer sees.
- **Slow work leaves the actor.** Waking the TV, searching for a download,
  scanning the offline cache and loading `library.db` run as tasks and come
  back as signals.
- **A remote key makes a round trip.** Every key goes to the core, which
  hands it to the player, to voice, or back to the screen as `Event::Key`.
  One path for the remote, the keyboard and mpv's window.
- **Tests reach the core without a screen.** `Core::detached` gives a handle
  with an in-memory database, for the API's tests and the actor's own.
